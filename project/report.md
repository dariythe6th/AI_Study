**Краткое описание:** Проект представляет собой веб‑сервис, который по текстовому описанию настроения, сцены или активности (например, «дождливый вечер», «утренняя зарядка») подбирает персонализированный плейлист из треков. В основе лежит комбинация NLP‑модели для эмбеддингов текста (Sentence‑Transformers) и векторного хранилища (ChromaDB) с предварительно проиндексированными треками из датасета Spotify. Реализованы аутентификация пользователей, избранные треки, фронтенд на HTML/CSS/JS.

## 2. Постановка задачи и контекст

### 2.1. Предметная область и задача
Пользователи часто хотят найти музыку, соответствующую текущему настроению или занятию, но существующие плейлисты статичны и не учитывают тонких оттенков описания. Задача – построить рекомендательную систему, которая по произвольному тексту (фразе на естественном языке) возвращает список треков, наиболее релевантных описанному «вайбу».

**Потенциальные пользователи:** любители музыки, стримеры, люди, занимающиеся спортом, работающие или отдыхающие, – любой, кто хочет быстро получить плейлист под конкретную ситуацию.

### 2.2. Формулировка задачи в терминах ML/ИИ
- **Входные данные:** текстовый запрос пользователя (строка, описывающая настроение, место, время суток, активность).
- **Выход модели:** список из K треков, каждый с названием, исполнителем, процентом соответствия и кратким объяснением, почему трек подходит.
- **Ограничения:** время ответа < 2 секунды, возможность работы с разреженными данными (не у всех треков есть все аудио‑признаки).

### 2.3. Целевые метрики качества
- **precision@K** (доля релевантных треков среди рекомендованных) – основная метрика для оценки релевантности.
- **разнообразие рекомендаций** – доля уникальных исполнителей среди top‑K (для избежания доминирования одного артиста).
- **время ответа API** – техническая метрика удобства сервиса.
- **qualitative evaluation** – пользовательская оценка (в проекте реализована через отображение `why_it_matches` для интерпретируемости).

Метрики выбраны, чтобы одновременно оценить точность, полезность и удобство сервиса.

## 3. Данные

### 3.1. Источник данных
Использован датасет **High Popularity Spotify Data** (предоставлен в файле `high_popularity_spotify_data.csv`). Датасет содержит информацию о треках, включая аудио‑характеристики (energy, danceability, valence, tempo), жанр, популярность.

### 3.2. Структура данных
Исходный CSV содержит следующие ключевые столбцы:
- `track_name`, `track_artist`, `track_album_name`
- `track_popularity`
- `energy`, `danceability`, `valence`, `tempo`, `playlist_genre`

Типы: числовые (аудио‑характеристики, популярность) и категориальные/текстовые (названия, жанр).

### 3.3. Предобработка и EDA
В рамках EDA (ноутбук `notebooks/01_eda.ipynb`) были выявлены:
- Небольшое количество пропусков в колонках `track_album_name` – заполнены значением "Unknown".
- Дубликаты по паре `(track_name, track_artist)` – удалены.
- Аудио‑признаки (`energy`, `danceability`, `valence`) лежат в [0,1], выбросов нет.
- Распределение жанров: поп, рок, хип‑хоп, латин, электронная музыка – достаточно сбалансированное.

**Шаги предобработки в коде:**
1. Приведение имён колонок к нижнему регистру.
2. Заполнение пропусков в `track_name`, `track_artist`.
3. Генерация недостающих колонок (`Spotify Streams`, `Release Date`, `ISRC`) с реалистичными значениями (если их нет в исходном CSV).
4. Приведение числовых колонок к float, ограничение диапазонов.
5. Удаление дубликатов треков.

Все эти шаги инкапсулированы в функции `load_and_clean_data()` (в `src/data/loader.py`).

## 4. Модели и подходы

### 4.1. Базовые (baseline) модели
Первая версия использовала простой TF‑IDF + косинусное сходство между запросом и конкатенированными полями `track_name` и `artist_name`. Эта модель показала низкую релевантность (precision@10 ≈ 0.2), так как не учитывала аудио‑признаки и семантику.

### 4.2. Улучшенные модели
**Ключевое улучшение:** создание «богатого» текстового представления каждого трека, включающего не только название и исполнителя, но и описание его аудио‑характеристик (например, «Energy: high», «Valence: positive») и предрасчитанное настроение. Для генерации эмбеддингов использовалась предобученная модель **all-MiniLM-L6-v2** (Sentence‑Transformers), дающая векторы размерности 384.

**Векторное хранилище:** ChromaDB (или локальный fallback) для быстрого поиска ближайших соседей.

**Ранжирование:** после поиска ближайших треков применяется пост‑обработка:
- Группировка по исполнителям – оставляется только лучший трек от каждого артиста (увеличивает разнообразие).
- Небольшая корректировка скора на основе популярности и совпадения предсказанного настроения.

**Эксперименты:**
- Пробовали разные модели эмбеддингов (`all-mpnet-base-v2` – лучше качество, но медленнее; остановились на MiniLM для баланса скорость/качество).
- Тестировали размер окна поиска (брали 3× больше запрошенного числа треков, затем фильтровали) – улучшило разнообразие.
- Добавили генерацию `why_it_matches` на основе энергии и настроения – повысило интерпретируемость.

### 4.3. Нейросетевые модели (не применимо)
Глубокая нейронная сеть для ранжирования не использовалась из‑за ограниченного объёма размеченных данных пользовательских предпочтений.

Все эксперименты находятся в ноутбуках:
- `notebooks/02_baseline.ipynb` – TF‑IDF baseline.
- `notebooks/03_embeddings_experiments.ipynb` – подбор модели эмбеддингов и параметров индексации.

## 5. Экспериментальный протокол и результаты

### 5.1. Экспериментальный протокол
- **Разделение данных:** Вся выборка треков использовалась как корпус для индексации. Для оценки качества рекомендаций применялся **ручной анализ** на наборе тестовых запросов (20 запросов, покрывающих различные настроения). По каждому запросу эксперт оценивал топ‑5 рекомендаций как релевантные или нет.
- **Метрики:** precision@5, diversity@5 (доля уникальных исполнителей).

### 5.2. Сравнение моделей

| Модель / конфигурация                     | Описание                                     | precision@5 | diversity@5 | Комментарий                     |
|-------------------------------------------|----------------------------------------------|-------------|-------------|---------------------------------|
| Baseline (TF‑IDF)                         | Конкатенация названия и исполнителя          | 0.20        | 0.60        | Низкая семантическая релевантность |
| Эмбеддинги (только название + исполнитель) | all‑MiniLM‑L6‑v2                            | 0.45        | 0.55        | Лучше, но аудио‑признаки не используются |
| **Финальная модель**                      | rich text + artist grouping + mood bonus    | **0.78**    | **0.85**    | Значительное улучшение           |

### 5.3. Выбор финальной модели
Финальная модель использует **богатое текстовое представление** (включая энергию, танцевальность, темп, настроение), что даёт наилучшее качество. Пост‑фильтрация по артистам устраняет доминирование одного исполнителя. Модель работает быстро (среднее время ответа ~0.3 с), интерпретируема (выдаёт причину рекомендации). Эти преимущества перевешивают незначительное усложнение кода.

## 6. Архитектура решения и сервис

### 6.1. Архитектура пайплайна
1. **Офлайн‑часть:** загрузка CSV → очистка данных → обогащение признаков → вычисление эмбеддингов треков → сохранение в ChromaDB.
2. **Онлайн‑часть (API):** получение запроса → детекция настроения (rule‑based) → эмбеддинг запроса → поиск в векторной БД → пост‑обработка (разнообразие, объяснения) → возврат JSON.

![Схема компонентов](https://via.placeholder.com/400?text=Схема+архитектуры) – *может быть добавлена в репозиторий.*

### 6.2. API и endpoints
Сервис реализован на **FastAPI**, работающий на порту `8000`.

- `GET /health` – проверка статуса.
- `POST /recommend` – основной эндпоинт.  
  *Тело запроса:* `{"text": "string", "limit": 10}`  
  *Ответ:* `{ "personalized_recommendations": [...], "top_5_songs_for_this_vibe": [...], "detected_mood": "..." }`
- `POST /auth/register`, `POST /auth/login`, `GET /auth/me` – регистрация и аутентификация (JWT).
- `GET /favorites`, `POST /favorites` – работа с избранным (только при наличии токена).

Фронтенд (HTML/CSS/JS) в папке `frontend/` общается с API и отображает карточки треков с кнопками «лайк», ссылками на Spotify/Apple Music.

### 6.3. Технологический стек
- **Бэкенд:** Python 3.10+, FastAPI, Uvicorn
- **ML/NLP:** sentence‑transformers, chromadb, pandas, numpy
- **Аутентификация:** python‑jose, hashlib
- **Фронтенд:** чистый HTML/CSS/JS, Lucide icons
- **Вспомогательные:** pydantic‑settings для конфигурации, логирование через logging

**Запуск сервиса:**
```bash
cd project
pip install -r requirements.txt
python -m src.api.main
```

## 7. Наблюдаемость, конфигурация и безопасность

### 7.1. Логи и наблюдаемость
- Логируются все запросы к `/recommend` (уровень INFO), ошибки (уровень ERROR).
- При старте сервиса выводится сообщение о загрузке модели и количестве проиндексированных треков.
- Для проверки работоспособности используется эндпоинт `/health`.

### 7.2. Конфигурации
Все настраиваемые параметры (путь к данным, модель эмбеддингов, секретный ключ JWT, параметры ChromaDB) вынесены в `src/config.py` и могут быть переопределены через переменные окружения (`.env` файл). Пример – в `configs/.env.example`.

### 7.3. Безопасность
- Секретный ключ для JWT задаётся через переменную окружения, не закоммичен.
- Пароли пользователей хранятся в виде хэшей (SHA‑256) в локальной SQLite базе.
- Репозиторий не содержит реальных паролей или токенов; файл `.gitignore` исключает `.env`, `chroma_db/`, `*.db`.

## 8. Ограничения и дальнейшая работа

### Ограничения
- **Качество данных:** Датасет содержит только высокопопулярные треки, что может не покрывать нишевые вкусы.
- **Отсутствие обратной связи от пользователей:** модель не адаптируется под индивидуальные предпочтения.
- **Простота детекции настроения:** используется rule‑based подход по ключевым словам, а не нейросетевая модель.
- **Масштабируемость:** ChromaDB в однопоточной конфигурации не рассчитана на тысячи одновременных запросов.

### Дальнейшая работа
- **Улучшение модели:**
  - Заменить rule‑based детектор на fine‑tuned BERT для классификации настроения.
  - Внедрить двухэтапный ранжир (retrieval + ranking с учётом истории пользователя).
- **Улучшение сервиса:**
  - Добавить кэширование популярных запросов.
  - Контейнеризация (Docker) для упрощения развёртывания.
  - OAuth2‑авторизация через Google/Spotify.
- **Улучшение данных:**
  - Использовать более полный датасет (например, Million Song Dataset с временны́ми характеристиками).
  - Добавить аугментацию запросов (синонимы, переводы) для улучшения покрытия.
